Le NIP-34 décrit git sur Nostr : comment un dépôt peut être annoncé et suivi au moyen d'événements Nostr ordinaires, plutôt que de dépendre uniquement d'une forge centralisée. La [PR #2312](https://github.com/nostr-protocol/nips/pull/2312), ouverte par DanConwayDev et fusionnée le 10 avril 2026, ajoute à ce NIP une spécification formelle pour les URL de clonage `nostr://`.

## Ce qu'est une URL de clonage nostr://

Une URL `nostr://` adresse un dépôt via le protocole lui-même, plutôt que via un remote HTTPS ou SSH pointant vers une forge précise. La nouvelle section de `34.md` définit trois formes pour cette URL :

```
nostr://<naddr>
nostr://<npub|nip05>/<identifier>
nostr://<npub|nip05>/<relay-hint>/<identifier>
```

L'`<identifier>` est la valeur du tag `d` de l'événement d'annonce de kind `30617` du dépôt, l'événement adressable que le NIP-34 utilise pour publier un dépôt. Le `<relay-hint>`, facultatif, indique au client un relais susceptible de porter les événements de ce dépôt, et son schéma `wss://` peut être omis par souci de concision. Lorsqu'un assistant `git-remote-nostr` est installé, une URL dans ce format peut être passée directement à `git clone`, de la même façon qu'un remote HTTPS le serait.

La description de la PR note que ce format était déjà utilisé avant que la spécification ne le rattrape. ngit comme shakespeare l'implémentent tous deux comme URL de clonage sous le nom `git-remote-nostr`, et il est affiché par des clients comme gitworkshop.dev et nostrhub.io. La CLI nak le prend en charge sans exiger NIP-05. L'inscrire dans le texte du NIP transforme une convention à laquelle plusieurs outils indépendants étaient déjà arrivés informellement en quelque chose contre lequel la spécification peut être vérifiée.

## Le défaut que la même PR corrige

Le NIP-34 recommande le kebab-case pour le tag identifiant `d` d'une annonce de dépôt, mais ne l'impose pas. Un dépôt dont la valeur `d` n'est pas en kebab-case, contenant des espaces ou des barres obliques par exemple, pouvait produire une URL `nostr://` ne correspondant ni à la spécification git-remote-helper, ni à aucune spécification d'URL.

Le nouveau texte comble cette lacune en imposant un encodage pourcentage : `<relay-hint>` comme `<identifier>` DOIVENT être encodés en pourcentage selon la RFC 3986 §2.1. Les exemples mêmes de la PR montrent pourquoi cela compte.

```
nostr://npub15qydau2hjma6ngxkl2cyar74wzyjshvl65za5k5rl69264ar2exs5cyejr/relay.ngit.dev/ngit
nostr://npub15qydau2hjma6ngxkl2cyar74wzyjshvl65za5k5rl69264ar2exs5cyejr/my%20%F0%9F%9A%80%20repo
nostr://danconwaydev.com/ws%3A%2F%2Flocalhost%3A7334/my-local-only-repo
nostr://danconwaydev.com/relay.ngit.dev/ngit
```

Le deuxième exemple porte un identifiant `d` contenant des espaces et un emoji, qui reste une URL valide une fois encodé en pourcentage. Le troisième porte une indication de relais écrite comme une simple adresse locale `ws://`, elle aussi encodée en pourcentage pour survivre une fois intégrée dans le segment de chemin de l'URL.

## Pourquoi cela compte pour git sur Nostr

Un dépôt accessible uniquement par HTTPS ou SSH dépend de l'endroit où ce remote unique se trouve hébergé. Une URL de clonage `nostr://` se résout au contraire via les relais : un `naddr`, ou un npub ou identifiant NIP-05 accompagné d'une indication de relais facultative, suffit pour retrouver l'annonce actuelle du dépôt, quelle que soit la forge ou le serveur qui le sert à ce moment-là. C'est cette partie du NIP-34 que cette PR rend précise : pas l'idée générale, antérieure à la PR, mais le format exact sur lequel des implémentations indépendantes doivent s'accorder pour que `git clone nostr://...` se comporte de la même façon sur ngit, shakespeare, gitworkshop.dev, nostrhub.io et nak.

Le changement lui-même est modeste, 22 lignes ajoutées et 1 supprimée dans `34.md`, mais il transforme une convention à laquelle plusieurs outils étaient déjà arrivés informellement en un texte contre lequel la spécification peut être testée.
