Работа Nostr WoT SDK с passkey теперь доступна под стабильными тегами npm. Реестр указывает [`@nostr-wot/identity` 1.1.0](https://registry.npmjs.org/@nostr-wot%2Fidentity) и [`nostr-wot-sdk` 3.0.1](https://registry.npmjs.org/nostr-wot-sdk) как версии `latest`. Оба пакета опубликованы 23 октября 2026 года из коммита, который объединил [стабильный выпуск](https://github.com/nostr-wot/nostr-wot-sdk/pull/23). Исходный код пакетов не изменился по сравнению с уже протестированными кандидатами.

Выпуск предназначен для разработчиков подписантов и приложений Nostr. Он делает режимы идентичности passkey явными, добавляет зашифрованные записи восстановления для нескольких управляемых хостом способов хранения и поддерживает подпись через провайдера для существующих учетных записей Nosskey.

## Производные и хранимые passkey отличаются

Пакет identity различает два режима. В производном режиме приватный ключ Nostr детерминированно вычисляется из результата WebAuthn PRF. В хранимом режиме этот результат защищает существующий приватный ключ, seed или vault с несколькими учетными записями.

Новые учетные данные получают маркированный идентификатор пользователя, который сообщает режим до чтения хранилища. Хранимый passkey никогда не интерпретируется как производный без явных данных. Если у старого немаркированного ключа недостаточно доказательств, `resolvePasskeyIdentity` возвращает `ambiguous` и предполагаемый публичный ключ. Приложение должно показать его пользователю и получить подтверждение до вывода секрета.

Такое разделение сохраняет непрерывность идентичности. Производный режим связывает идентичность с вычислением passkey. Хранимый режим позволяет заново защитить ту же идентичность под другим relying party, если хост намеренно импортирует и повторно шифрует ее.

## Восстановление остается под контролем хоста

[`@nostr-wot/identity/vault`](https://github.com/nostr-wot/nostr-wot-sdk/blob/384023f947e7dcfe4d54f7862308cdf78040067c/docs/passkey-recovery.md) предоставляет переносимую криптографию, проверку записей и координацию. Пакет не вызывает аутентификаторы и не открывает соединения с реле. Хост предоставляет WebAuthn или нативный клиент, транспорт, подпись и проверку событий, а также интерфейс согласия.

Запись может содержать один ключ или vault с несколькими учетными записями. Шифрование аутентифицирует тип, ID relying party, автора и ID учетных данных. Перед записью провайдер должен прочитать существующее хранилище. Любой непустой blob требует явного подтверждения перезаписи, даже если прежние данные невозможно декодировать. Отказ или ошибка не приводят к скрытому переходу на реле.

Восстановление через реле тоже требует явного выбора. Хост разрешает его, указывает реле и получает хотя бы одно подтверждение. Новые записи используют предварительный kind `31778`, который пока не зарезервирован NIP. Старые форматы остаются читаемыми. Локальная запись или ответ реле подтверждают только эту операцию, но не возможность восстановления на другом устройстве.

## Два пути для существующих учетных записей Nosskey

[`nostr-wot-sdk` 3.0.1](https://github.com/nostr-wot/nostr-wot-sdk/pull/22) читает явные резервные копии Nosskey с прямым ключом или ключом в обертке NIP-44 и сохраняет исходные входы PRF. Восстановленный публичный ключ сверяется с копией, а при нехватке доказательств библиотека не переключается на другой режим.

Приложения, которые не хотят импортировать приватный ключ, могут использовать `NosskeyIframeSigner`. Он фиксирует окно iframe, HTTPS-источник и выбранную учетную запись, проверяет содержимое событий и подписи, ограничивает время запросов и требует явного закрытия. Согласие провайдера и поддержка браузера остаются внешними условиями.

## Что меняется для интеграторов

Стабильные пакеты устанавливаются без prerelease-тега:

```bash
npm install @nostr-wot/identity@1.1.0 nostr-wot-sdk@3.0.1 nostr-tools
```

Хосту по-прежнему нужны тесты аутентификаторов и синхронизации на реальных устройствах. Он должен сохранять неизвестные поля при перезаписи vault, очищать буферы секретов, подтверждать публичный ключ при миграции и объяснять место хранения восстановления. Записи являются снимками и требуют обновления после изменения учетных записей.

Стабильные теги делают проверенные API устанавливаемыми без `next`. Они не превращают passkey в универсальную резервную копию. Разрешение relying party остается решением о доверии, предварительный kind может измениться, а каждое приложение отвечает за согласие, долговечность хранения и проверяемое восстановление.
