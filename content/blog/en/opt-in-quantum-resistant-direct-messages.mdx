There is an obvious way to add post-quantum encryption to a messaging protocol. Both clients advertise what they support, they agree on the strongest thing they have in common, and the user never has to know. That is roughly how TLS works, and it has served the web well for thirty years.

We built the opposite. Post-quantum encryption in the [Nostr WoT extension](https://github.com/nostr-wot/nostr-wot-extension) is opt-in: a client has to ask for it explicitly, by name, passing the recipient's key. Nothing negotiates anything on your behalf.

That was not laziness, and it is worth explaining, because the same decision is coming for every messaging protocol that adds post-quantum support.

## The failure that decided it

Post-quantum encryption rides on an optional third argument to an existing function. A caller asks for ordinary encryption like this:

```js
window.nostr.nip44.encrypt(pubkey, plaintext)
```

and for post-quantum encryption like this:

```js
window.nostr.nip44.encrypt(pubkey, plaintext, { scheme: 'pq', recipientKemKey })
```

Now consider what happens when a client sends the second call to a signer that has never heard of post-quantum anything.

JavaScript discards surplus arguments silently. The old signer ignores the third one, encrypts the message the way it always has, and hands back a perfectly valid ciphertext. No error. No warning. Nothing in the return value distinguishes it from the post-quantum one, because a ciphertext is a ciphertext.

The client then shows the user a badge saying the message is protected against quantum attack. It is not. It has exactly the protection it had last week, and the user has been told otherwise.

**A silent downgrade dressed as protection is worse than no protection at all.** Someone who knows their messages are ordinary encrypted messages behaves accordingly. Someone who has been told they are quantum-safe does not.

## Ask, do not guess

The fix is not clever. The signer publishes what it accepts:

```js
window.nostr.nip44.schemes  // ["nip44", "pq"]
```

A client checks that list before it promises anything:

```js
const supportsPq =
  Array.isArray(window.nostr?.nip44?.schemes) &&
  window.nostr.nip44.schemes.includes('pq');
```

The marker is additive, so every existing caller is untouched. And it distinguishes two things that look identical from the outside but are not the same at all:

- **No `schemes` property.** An older signer. Its capability is unknown.
- **`schemes` is `["nip44"]`.** A signer stating that it does not do post-quantum.

Both mean "do not send post-quantum". Only the second is an answer. A client that wants to tell a user whether the obstacle is on their side or their signer's needs to know which one it is looking at.

## Why not negotiate automatically

The tempting alternative is for the signer to work it out. If the recipient has published post-quantum keys, use them; otherwise fall back.

The signer cannot do this, and the reason is structural rather than a missing feature.

Post-quantum encryption needs the recipient's ML-KEM public key. The signer does not have it. It lives in a `kind:10203` event on a relay, which means inferring the scheme would require the signer to fetch from the network *in the middle of a signing call*. That is an operation callers expect to be local and immediate, now carrying latency and a failure mode.

Then ask what happens when that lookup fails. There are two options. Throw, and break every existing caller. Or fall back to classic encryption silently, which is the exact failure at the top of this article, reintroduced by the mechanism meant to prevent it.

The calling application already knows whether it wants post-quantum. It already has the recipient's attestation, or knows what to do when it does not, and it is the layer that can actually tell the user what happened. So the decision belongs there, and it passes the key it already holds.

## Decryption takes no flag

Only one direction is opt-in. Decryption is automatic, and that asymmetry is deliberate rather than an inconsistency.

The post-quantum payload is self-describing: it leads with a version byte and an algorithm byte. A signer reads those and routes the payload without being told anything. A caller cannot get it wrong, because it is never asked.

The rule underneath both halves is the same. **Infer when the data can tell you the answer; ask when it cannot.** On the way in, the ciphertext knows what it is. On the way out, nothing knows except the application.

## What a user actually sees

Three states, not two, and the difference matters more than it looks.

| State | What holds |
| --- | --- |
| **Extra safe** | Messages are unreadable, nobody can see who you are talking to, and a future quantum computer could not open them |
| **Safe** | Messages are unreadable and nobody can see who you are talking to, but a quantum computer could open them one day |
| **Basic** | Messages are unreadable, but the servers carrying them can see who you are talking to |

Most conversations sit in the middle, and the middle is genuinely good news. [NIP-17](https://github.com/nostr-protocol/nips/blob/master/17.md) gift wrap already hides who is talking to whom, which is real protection working right now. An interface that reduces this to a binary, quantum-safe or not, says nothing about the protection the user does have, and it turns the common case into a permanent warning that people stop reading.

[Obelisk](https://obelisk.ar) shows this as a single icon in the conversation header. Not a banner. A standing warning about the state nearly every Nostr conversation is in, and will stay in for a while, is furniture within a week.

## Opt-in is not the same as off

Opt-in describes where the decision is made, not how much friction the user faces.

In practice a user turns post-quantum keys on once, in their signer, and never thinks about it again. From then on the client asks for post-quantum encryption whenever the person on the other end has published keys too. The explicit call happens between the client and the signer, dozens of times a day, without anybody looking at it.

What opt-in buys is that the promise shown to the user and the cryptography actually performed cannot drift apart. Nothing silently decides on their behalf, so nothing can silently decide wrong.

## The specifications

The capability marker and the envelope format are written up as public drafts, so a second implementation can interoperate without reading our source:

- [Draft 04: signer encryption capability](https://github.com/nostr-wot/nostr-wot-extension/blob/main/nips/04-nip07-encryption-capability.md): `schemes`, the `encrypt` opt-in, and why the two are one design
- [Draft 03: the post-quantum NIP-44 envelope](https://github.com/nostr-wot/nostr-wot-extension/blob/main/nips/03-pq-nip44-envelope.md): the wire format that makes decryption inferable
- [Draft 02: key attestation](https://github.com/nostr-wot/nostr-wot-extension/blob/main/nips/02-pq-key-attestation.md): the `kind:10203` event a sender reads the recipient's key from
- [Draft 01: key derivation](https://github.com/nostr-wot/nostr-wot-extension/blob/main/nips/01-pq-key-derivation.md): deriving the keys from the seed phrase you already have

None of them has a NIP number yet. Disagreement about the wire format is more useful now than after a second client ships against it.

The identity half of this work is covered in [post-quantum Nostr identities](/blog/post-quantum-nostr-identities), the implementation write-up is on [QuantaKrypto](https://quantakrypto.com/blog/obelisk-first-nostr-client-post-quantum-dms), and if you just want to switch it on, Obelisk has a [step-by-step guide](https://obelisk.ar/guides/quantum-safe-dms).
